# Recruiter OS

מערכת SaaS לניהול גיוס, בנויה סביב האופן שבו רכז גיוס פרילנסר באמת עובד: מאגר מועמדים,
משרות, לקוחות, פייפליין, עמלות וגבייה — במקום אחד, בעברית ו-RTL מהיום הראשון.

> **הערה על הריפו:** האפליקציה הזו עצמאית לחלוטין ויושבת ב-`recruiter-os/`. היא לא נוגעת
> באפליקציית ה-Expo ובשרת `backend/` שנמצאים בשורש הריפו.

---

## הפעלה מהירה

```bash
cd recruiter-os
npm install
cp .env.example .env.local          # ערוך והגדר AUTH_SECRET
npm run db:seed                     # יוצר חשבון דמו עם נתונים מלאים
npm run dev                         # http://localhost:3100
```

התחברות לחשבון הדמו: `demo@recruiter-os.local` / `demo1234`

פקודות נוספות:

| פקודה | מה היא עושה |
|---|---|
| `npm run dev` | שרת פיתוח |
| `npm run build` / `npm start` | build ל-production והרצה |
| `npm test` | 54 בדיקות על הלוגיקה הקריטית |
| `npm run typecheck` | `tsc --noEmit` |
| `npm run db:migrate` | הרצת מיגרציות |
| `npm run db:seed` | יצירת חשבון דמו + נתונים |
| `npm run db:reset` | מחיקת ה-DB והקבצים שהועלו |

## הסטאק ולמה הוא נבחר

| רכיב | בחירה | נימוק |
|---|---|---|
| Framework | Next.js 15 (App Router) + React 19 | Server Components → פחות JS ללקוח, טעינה מהירה בנייד |
| שפה | TypeScript strict | הסכמה, ה-API והטפסים חולקים טיפוסים |
| DB | SQLite דרך `node:sqlite` | אפס תלויות native, קובץ אחד, מיגרציות SQL אמיתיות |
| עיצוב | Tailwind + CSS variables | RTL, מצב כהה ובהיר, ללא ספריית UI כבדה |
| ולידציה | Zod | סכמה אחת משמשת גם את ה-API וגם את הטפסים |
| AI | שכבת ספקים (מקומי / Claude) | עובד ללא מפתח, משתדרג עם מפתח |

**החלפת מסד הנתונים:** כל הגישה לנתונים עוברת דרך ממשק `Db` יחיד
(`src/lib/db/index.ts`) ודרך ריפוזיטורי גנרי שכופה `org_id`. מעבר ל-Postgres = מימוש
נוסף של אותו ממשק + מיגרציות בדיאלקט המתאים, בלי לגעת בקוד הדומיין.

## מודל הנתונים

21 טבלאות רלציוניות. **בכל טבלה עסקית יש `org_id`, וכל שאילתה עוברת דרך ריפוזיטורי
שמוסיף אותו** — כך שאי אפשר "לשכוח" `WHERE org_id = ?` ולדלוף מידע בין משתמשים.

```
users ─┬─ memberships ─── organizations ─┬─ stages (סטטוסים/שלבים ניתנים להתאמה)
       └─ sessions                       ├─ clients ─── client_contacts
                                         ├─ candidates ─┬─ candidate_attributes  (רישיונות/הסמכות/כישורים)
                                         │              ├─ candidate_experiences
                                         │              ├─ candidate_documents
                                         │              └─ candidate_tags ─── tags
                                         ├─ jobs ─┬─ job_requirements
                                         │        └─ job_tags
                                         ├─ applications ─── interviews
                                         ├─ placements ─── payments
                                         ├─ tasks · messages · notes
                                         ├─ automations ─── automation_runs
                                         └─ activity_events (ציר הזמן)
```

מידע חשוב נשמר **מובנה, לא כטקסט חופשי**: רישיונות והסמכות הם שורות ב-
`candidate_attributes`, ודרישות משרה הן שורות ב-`job_requirements`. זה מה שמאפשר
למנוע ההתאמה לענות על "מי עם רישיון C באזור חיפה" באמת.

## מה עובד באמת

### מנוע התאמה עם הסבר
דטרמיניסטי, רץ מקומית, ומסביר כל ציון. שש דימנסיות: דרישות (40), התאמת תפקיד (15),
מיקום (15), ציפיות שכר (10), זמינות (10), ניסיון (10). **דרישת חובה שלא מתקיימת חוסמת
את הציון** במקום להוריד אותו קצת. לכל התאמה מוצג פירוט: אילו דרישות מתקיימות ומהי
העדות לכך, מה חסר, המרחק בק"מ ומרכיבי הציון.

המרחק מחושב מגזטיר של ~48 ערים בישראל (`src/lib/geo.ts`), ווריאציות כתיב מנורמלות —
`רישיון C`, `רשיון c` ו-`רישיון ג'` הם אותו דבר.

### קריאת קורות חיים
חילוץ טקסט מ-PDF, DOCX, RTF ו-TXT **ללא שום ספריית צד שלישי** — מימוש ישיר מול
פורמט הקובץ (inflate של streams ב-PDF, קריאת ZIP ידנית ל-DOCX, כולל מחרוזות
UTF-16BE שבהן נכתבת עברית). לאחר מכן מזוהים שם, טלפון, מייל, עיר, רישיונות,
הסמכות, ניסיון והשכלה.

**מה שלא נמצא במסמך — נשאר ריק ומדווח למשתמש.** המערכת לא ממציאה שדות. בהעלאה
לפרופיל קיים מולאו רק שדות ריקים; מה שהוקלד ידנית לא נדרס.

### אוטומציות
כללים שרצים על אירועי אמת (מועמד נוסף, הודעה נשלחה, מועמד נשלח ללקוח, השמה נוצרה).
כלל מיידי רץ מיד; כלל מושהה נשמר כ-`automation_run` ממתין ומתבצע כשהזמן מגיע.
תשובה של מועמד **מבטלת** את המעקב שתוזמן. לכל כלל יש מתג הפעלה ולוג הרצות.

### הכסף
כל השמה מחשבת עמלה (אחוז משכר או סכום קבוע), פותחת תשלום צפוי לפי תנאי התשלום של
הלקוח, מסמנת תקופת אחריות, וסוגרת את המשרה כשכל התקנים אוישו. תשלום שעבר את תאריך
היעד מסומן אוטומטית כ"באיחור".

### מה לעשות עכשיו (Next Best Action)
שמונה כללים מדורגים לפי דחיפות: לקוח שממתין לפידבק, משימות באיחור, מועמד שלא חזר,
משרה פתוחה זמן רב עם מעט מועמדים, ראיונות היום, תשלומים באיחור, השמות שלא אושרו,
ומועמדים חדשים שטרם נוצר איתם קשר.

## AI — מה רץ ואיפה

שני ספקים מאחורי ממשק אחד (`src/lib/ai/types.ts`):

| | `AI_PROVIDER=local` (ברירת מחדל) | `AI_PROVIDER=anthropic` |
|---|---|---|
| קריאת CV | חוקים דטרמיניסטיים | Claude, עם נפילה חזרה למנוע המקומי |
| ניסוח הודעות | תבניות עברית לפי סגנון | Claude |
| צ'אט | הנתונים שאוחזרו, מוצגים כתשובה | Claude מנסח את אותם נתונים |
| **התאמה מועמד↔משרה** | **תמיד מקומי** | **תמיד מקומי** |

**האחזור תמיד מקומי ותמיד מוגבל לארגון של המשתמש.** הספק החיצוני מנסח עובדות
שנמסרו לו; הוא לא ניגש למסד הנתונים. כל קריאה ל-Claude נופלת בחזרה למנוע המקומי
אם היא נכשלת, כך שתקלת רשת לא שוברת שום זרימת עבודה.

## אינטגרציות — בלי להעמיד פנים

אין ספק שליחה מחובר, ולכן **המערכת לא מתיימרת לשלוח**. `MockChannel` מחזיר
`delivered: false` עם סיבה בעברית, ההודעה נשמרת בהיסטוריה של המועמד כטיוטה,
והמשתמש מקבל כפתור שפותח את ההודעה בוואטסאפ. הממשקים (`MessagingChannel`,
`CalendarService`) מוכנים — חיבור ספק אמיתי הוא מימוש אחד ומשתנה סביבה.

יומן: יצירת קובץ `.ics` תקני עובדת כבר עכשיו, כי היא לא דורשת חשבון חיצוני.

## אבטחה ופרטיות

- **סיסמאות**: scrypt (N=16384) עם salt לכל סיסמה; הפורמט מתעד את הפרמטרים כדי שניתן
  יהיה לחזק אותם בעתיד. השוואה ב-timing-safe, ובכניסה כושלת מורץ hash גם כשהמשתמש
  לא קיים — כדי לא להדליף אילו כתובות רשומות.
- **Sessions**: העוגייה מכילה טוקן אקראי; ב-DB נשמר רק HMAC שלו. `HttpOnly`,
  `SameSite=Lax`, `Secure` ב-production, פקיעה אחרי 30 יום.
- **Rate limiting**: מגובה DB (שורד restart) — התחברות לפי כתובת מייל ולפי IP, הרשמה,
  וכל endpoint מאומת.
- **בידוד בין משתמשים**: נאכף בשכבת הריפוזיטורי, לא בקריאה. הריפוזיטורי גם מסנן
  שדות שאינם עמודות אמיתיות ואוסר שינוי `org_id` — יש על זה בדיקות.
- **קבצים**: נשמרים מחוץ ל-`public/` עם שם מגונרר, הורדה רק דרך route מאומת שבודק
  בעלות, כולל הגנה מפני path traversal ואימות סוג וגודל.
- **סודות**: אך ורק ממשתני סביבה, דרך מודול `env` יחיד. ב-production חסר
  `AUTH_SECRET` = כשל בעלייה, לא ברירת מחדל שקטה.
